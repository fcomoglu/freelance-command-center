# 9. Code-first API contract with generated TypeScript types

- Status: accepted
- Date: 2026-11-19

## Context

Web, mobile and the extension share one REST API and must stay in sync with it. The contract also needs stable
conventions for IDs, pagination and errors before the first endpoint is written, because changing them later breaks
every client.

## Decision

- **Code-first contract:** springdoc generates the OpenAPI document; it is committed in `packages/api-client` and CI
  fails when it is out of date, so contract changes are visible in every pull request.
- **Client:** `openapi-typescript` generates types only; `openapi-fetch` and `openapi-react-query` provide the typed
  runtime. No generated runtime code.
- **IDs:** UUIDv7, generated by the application.
- **Pagination:** cursor-based (keyset) for every list.
- **Errors:** RFC 9457 Problem Details with a stable `code` that clients translate.

## Consequences

- A single developer changes the contract and its consumers in one commit; the diff of `openapi.json` doubles as
  the contract review.
- The spec can only be as precise as the annotations and DTOs: validation constraints and nullability must be
  declared in code.
- UUIDv7 keys are time-ordered (index-friendly) and not guessable, at 16 bytes per key.
- Cursor pagination does not offer total counts or jumping to a page number.
